## Findings

[MAJOR] KS/tasks/WP27-c-graph-and-action-walk.md:94-95 (T160) - "`enhancerOut` skips `action:` targets" is unconditional, yet the same bullet says "a step enhancement with an enhances edge to anything but one `action:` keeps E6 as built". Code: PK/domain/InForceResolution.java:333-336 treats an empty target set as "not an enhancer". So if every action target is skipped, these become in force unconditionally: (a) a step enhancement with two `action:` targets, whose bindingOf has no single target and so no binding; (b) an enhancer of any other kind whose only targets are actions. Today both are pruned. C36 (rules page :345-351) does NOT guarantee one target. It refuses cycles, chains that end at an enhancer, enhances∧overrides, and self_override. The one-target check is the ADR-0066 compose check, which lands after PR C. For case (a) with targets in two mission types M1 and M2, any choice of M would be settled by Set iteration order. - Recommendation: skip action targets and derive M only when the source is `STEP_ENHANCEMENT` and its merged `enhances` set is exactly one `action:M/s`. Every other shape keeps E6 as built, meaning the action targets count and are never in the set. Add red tests for two-action and other-kind→action enhancers (both stay pruned with ENHANCED_TARGET_NOT_IN_FORCE).
[MAJOR] PK/application/ClosureView.java:200-203 vs WP27:94 - `bindingOf` is to read "the step enhancement's enhances edge in the merged edges". `resolutionEdges().record` drops every edge whose target is not a merged winner. An enhancement that targets an `action:M/s` no closure pack declares therefore reaches InForceResolution with no enhances entry, and has neither enhancer nor binding. So with M deselected it is ACTIVE, which breaks OD-6's "exactly when M is in force". Today the same shape is already ACTIVE, an existing bug that OD-6 should close rather than inherit. - Recommendation: either derive the step-enhancer binding in ClosureView from the merged EdgeIndex before the winners filter and pass it in `Edges.bindings` (ClosureView.java is already on WP27's shared list; widen that entry), or prune an undeclared step target with ENHANCED_TARGET_NOT_IN_FORCE. Add a red test with the target action not declared and M deselected.
[MAJOR] WP27:90-93 vs :94-97 (E6 vs OD-9 consistency) - E6 binds by the target's URN alone. The node predicate and `action_not_found` use StepHolding ("P defines M and declares M/s"). A step enhancement whose target is declared by a pack that does not define M (the case OD-9 excludes) is ACTIVE under E6. Its target is then neither a graph node nor walkable, so E15 drops the enhances edge and E12/E16 show an enhancer with no target. That contradicts I11 (rules page :952, "no enhancer stands alone") on the reads. - Recommendation: get an explicit ruling. Either E6 grounds a step enhancer on "its single target is a held step (StepHolding) ∧ M ∈ X", or WP29 records the I11 gap as a divergence until the ADR-0066 compose check closes it. Pin the chosen answer with a test either way.
[MAJOR] KS/plan.md (new section, OD-9 bullet) and WP27:88-91 - StepHolding is defined "over composition facts" (per pack, unmerged). The merge treats `action:M/s` as a URN of its own: PK/domain/LayerMerge.java:68-76 and :291-299. Only within one level does a step's contest share M's settlement (:384-392). Across levels, if Q (project) replaces `mission_type:M` without declaring `action:M/t`, built-in P's `action:M/t` stays the only holder, so it wins, and StepHolding(P, M/t) is true. The walk would then start at, and `action_not_found` would accept, a step of a losing M version, against C17/C18 ("replaced whole, nothing of a losing version is read"). The same happens in one level when the settled sibling of M does not declare the step. - Recommendation: give StepHolding two explicit forms. One is per pack, for compose time and the other mission's FR-009. The other is merged: the winning place of `action:M/s` is held by the pack that wins `mission_type:M`, and is the form the node predicate, stepsOf and the walk use. Alternatively, rule that steps survive independently and record that as a divergence. Do not leave the choice implicit.
[MAJOR] KS/decisions/DM-01M702A71YF7WNDTG2AA89K8ZA.md + WP27:99-103 - "Eff plus held steps" is stated as the predicate of the whole walk. E16 says the walk is "over E_M restricted to Eff" (rules :872), and only the start node `action:mt/a` needs widening. If held steps are walkable, any requires/suggests/vocabulary edge into an action would list a step as an EffectiveArtifact entry, and the response can only hold artifacts. A step would also become a walk node, a predecessor of other entries (ADR-0018 D3), which changes via/hops. - Recommendation: the action-context walk admits a held step only as the start node; walked and listed nodes are Eff. The graph projection (E15) uses Eff ∪ held steps (EffectiveGraphNode is Urn+NodeKind and can carry them). Write the two predicates separately in E15/E16 (T165) and test that no step is ever listed.
[MAJOR] KS/tasks/WP28-c-contract-graph-context.md:103-106 (T164) - "EffectiveSkippedReport.RequiredNotInForce.reason is narrowed to the two-value type WP27 introduces". EffectiveSkippedReport is in activations.domain, so using a packs.domain type there breaks C-002/HexagonalArchitectureTest. Pinning ActivationWireTokenParityTest (activations infra/api) "against that type" makes the same cross-slice reach in a test. Today ClosureViewSession maps by `valueOf(name())` (:223). - Recommendation: activations.domain gets its own two-value enum (for example `EffectiveSet.PruningReason`). ClosureViewSession maps it with an exhaustive switch, not by name. The parity row pins the contract to the activations enum and drops PRUNING_REASONS. A test in infra.packs pins that the packs→activations mapping is total. Reword T164 to say this.
[MINOR] WP27:92, WP29 T165 text ("a selected step enhancer is in force exactly when...") - E6 is a grounding condition. A selected step enhancer can still be out of force when it is hidden by an override (E4), denied, or language-filtered. The other mission's plan says "grounded exactly when" (its OD-6 text, plan.md:1048). - Recommendation: write "grounded (E6) exactly when the mission type of its single enhances target is in force", and keep E9's row order.
[MINOR] WP28:113-117 and WP27:101 - "template, asset, guard, lifecycle ... are never in force" is false in packs. contracts/packs/schemas/policy.schema.json:69 admits locks on all four, and InForceResolution.java:137-141,166-173 puts a locked one in force with reason LOCKED. They are absent from Eff only because ClosureViewSession.activatable() (:229-231) drops them. - Recommendation: write the divergence as "not activatable, so absent from the effective reads even when a lock puts them in force", and pin a locked template that is ACTIVE in InForceStates and absent from the graph.
[MINOR] InForceResolution.java:252-283 (E7 with OD-6) - A step enhancement SE that `overrides mission_type:M` while enhancing `action:M/s` is not refused by C36, because the two edges name different targets. Under OD-6 the sequence is: SE hides M, SE is pruned and withdrawn, M comes back, SE is grounded again with its overrides withdrawn, and every read answers 500 override_unstable. Under E6 as built this closure was stable. That is a new failure mode. - Recommendation: add a test that pins the refusal, and ask whether C36 should refuse "an artifact overrides the mission type it is bound to" at registration (record it in WP29 if deferred).
[MINOR] WP28:96-101 (T163) - After OD-6 a well-formed step enhancer never reaches enhancedTargetNotInForce. The bindingOut row comes first (InForceResolution.java:463-468), so it lands in missionTypeNotInForce. `action:` targets in EnhancerWithoutTarget now come only from the shapes in finding 1. - Recommendation: build the T163 tests on those shapes, so the NodeReference step-target test is not vacuous.
[MINOR] contracts/charter/schemas/NodeKind.yaml:6-22 vs kernel NodeKind.java:38-41 - the contract enum lacks guard and lifecycle, so `NodeReference {kind: NodeKind, id}` cannot name them. EffectiveGraph already names nodes by `Urn` strings (EffectiveGraphEdge/Node), and ArtifactReference uses `artifactId`, not `id`. - Recommendation: state the reuse surface in NodeReference's description: use it where a skipped-report or object field names a node that may be a step; graph positions stay Urn; ArtifactReference stays activatable-only. Note the guard/lifecycle gap, or the kernel/contract parity rule that excuses it.
[MINOR] InForceResolution.java:366-371 - `satisfiedBy` and `overriddenBy` take the smallest URN when two overriders in force reach the target. That is a tie settled by URN order, and no rule cites it (the rules page has no "smallest" in E5/E9). - Recommendation: T165's "explicit rulings, never accidental order" sweep should state this as a ruling on E9, or report every overrider.
[MINOR] WP28:79,116 (T138 layerOverrides) and the node/edge lists of E15 - no output order is specified. ClosureViewSession.overridesOf (:148-156) emits in LayerMerge's first-hold closure order. - Recommendation: sort nodes and edges by URN (source, relation, target) and layerOverrides by (urn, loser level, loser pack), and pin byte-stability as SkippedReport does.

What holds: the fixed point stays monotone (bindingOf is static, so the least fixed point and its bound are unchanged). E7 re-runs do not depend on the new binding. The walk's parent tie (ADR-0018 D3: smallest URN) is an explicit ruling.
